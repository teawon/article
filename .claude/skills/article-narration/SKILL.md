# 아티클 낭독 대본 보정 스킬

`scripts/collect.mjs` 가 수집한 원문(긱뉴스 요약)을, **운전하며 소리만 들어도 이해되고 흐름을 놓치지 않는** 한국어 낭독 대본으로 재작성한다.

## 입력 / 출력

- 파일명 `<key>.json` 의 key 는 전역 키 형식 `"<provider-slug>__<소스ID 또는 URL해시>"` (예: `geeknews__31806`). collect.mjs 가 정한다.
- 입력: `data/raw/<key>.json` — `{ id, sourceId, title, source, provider, link, published, paragraphs, comments }`. `paragraphs` 는 원문 문단 배열, `comments` 는 독자 댓글 본문 배열(없을 수 있음). `id` 가 곧 key.
- 출력: `data/narrated/<key>.json` — `{ id, sourceId, title, source, provider, link, published, tags, script }` (재작성한 낭독 대본 + 주제 태그)
- **보정 여부는 파일 존재로 판단한다**: `data/narrated/<key>.json` 이 이미 있으면 그 글은 **건너뛴다** (사용자가 "전부 다시"라고 하면 예외로 덮어쓴다)
- `data/seen.json` 은 collect.mjs 가 관리하는 수집 장부다. **스킬은 건드리지 않는다.**

## 실행 절차

1. `data/raw/` 의 파일 목록을 읽는다.
2. 각 `<key>` 에 대해 `data/narrated/<key>.json` 이 **없는 것만** 처리한다.
3. 해당 원문(`paragraphs` + `title` + `source`)을 아래 "대본 작성 규칙"으로 대본화한다.
4. 원문의 `id/sourceId/title/source/provider/link/published` 를 그대로 두고 `paragraphs` 대신 `script`(낭독 대본)와 `tags`(주제 태그 배열)를 넣어 `data/narrated/<key>.json` 으로 저장한다.
5. 몇 개를 보정했는지, 각 글 제목을 사용자에게 보고한다.

## 태그 분류 규칙

각 글에 아래 **정해진 태그 세트**에서 해당하는 것만 `tags` 배열로 넣는다 (0~여러 개, 맞는 게 없으면 빈 배열 `[]`). 새 태그를 임의로 만들지 않는다 — 필터 일관성을 위해.

| 태그 | 기준 |
|------|------|
| `AI` | LLM·에이전트·모델·머신러닝·AI 제품/전략/인프라 등 AI가 핵심 소재 |
| `프론트엔드` | 웹 UI 개발, 브라우저, CSS/JS 프레임워크, 프론트엔드 실무 |
| `백엔드·인프라` | 서버, DB, 배포, 성능/시스템 프로그래밍, 인프라 |
| `도구` | 직접 만든/소개하는 유틸·앱·오픈소스 도구 (Show GN 류 포함) |
| `디자인` | UI/UX 디자인, 타이포그래피, 제품 디자인 판단 |
| `제품·비즈니스` | 창업·수익화·시장·전략·조직 운영 |
| `커리어` | 개발자 성장·취업·일하는 방식 |

- 제목만 보지 말고 **내용(paragraphs)으로 판단**한다 (예: 제목이 추상적이어도 본문이 AI 얘기면 `AI`).
- 억지로 채우지 않는다. 뉴스·에세이 등 어디에도 안 맞으면 `[]`.

## 대본 작성 규칙 (핵심)

운전 중 청취가 목적이다. **놓쳐도 다시 따라잡을 수 있는 구조**가 최우선.

### 1. 구조 — 3단 (예고 → 본문 → 정리)

**(가) 예고 (Signpost)** — 글 시작에 항상:
- 앞 글과 구분되는 전환 인사: `"다음 글입니다."` / 첫 글이면 `"오늘의 첫 소식입니다."`
- 이 글이 **무엇에 관한 것인지 한 문장**: `"이번 글은 ○○에 대한 이야기입니다."`
- **핵심 결론을 미리 한 문장**: `"핵심부터 말씀드리면, ○○입니다."`
  → 여기서 요점을 먼저 줘서, 뒤를 놓쳐도 결론은 건지게 한다.

**(나) 본문** — 원문 문단들을 의미 단위로 묶어 순서대로:
- 각 묶음 앞에 **무슨 얘기를 할지 예고**: `"먼저, ~"`, `"다음으로, ~에 대한 부분입니다."`, `"여기서 중요한 점은,"`
- 내용을 자연스러운 구어체로 풀어서 설명
- 각 의미 묶음 끝에 **한 줄 요약**: `"정리하면, ~라는 것입니다."` (문단이 짧으면 생략 가능)

**(다) 마무리** — 글 끝에 항상:
- **핵심 재요약**: `"이 글의 핵심을 다시 정리하면, ○○입니다."`
  → 놓친 사람도 마지막에 요점을 한 번 더 잡게 한다.

**(라) 댓글 반응** — `comments` 가 있고 내용이 유의미할 때만, 마무리 뒤에 덧붙인다:
- 시작: `"끝으로, 이 글에 대한 댓글 반응입니다."`
- 독자들의 **찬반과 주요 의견**을 요약한다. 대립이 있으면 양쪽을 다 전한다.
  예: `"○○라며 공감하는 의견이 있는 반면, △△라는 반론도 있었습니다. 그밖에 □□라는 지적도 눈에 띕니다."`
- 규칙:
  - 단순 감탄사·이모지·인사("ㅋㅋ", "굿" 등)뿐이거나 댓글이 없으면 이 섹션은 **생략**한다.
  - 실제 댓글에 있는 내용만 전한다(없는 주장 지어내지 않기). 특정 개인을 비방하는 표현은 중립적으로 순화한다.
  - 2~5문장 정도로 간결하게. 댓글이 많으면 대표적인 관점 위주로 압축한다.

### 2. 문체

- **자연스러운 구어체 "합니다"체.** 개조식("~함", "~임", "~음")은 **반드시** 서술형으로 바꾼다.
  - ✗ "작동하기 어려움" → ✓ "작동하기 어렵습니다"
- 문장은 **짧게.** 한 문장에 한 가지 정보. 긴 문장은 두세 개로 나눈다.
- 접속·전환어("그런데", "그래서", "반면에", "예를 들어")로 흐름을 자연스럽게 잇는다.

### 3. 전문용어 · 영어 · 기호 (운전 중이라 특히 중요)

- 영어·약어는 **한국어 발음으로 적고, 필요하면 짧게 풀어 설명**한다.
  - `SWE-bench` → `"에스더블유이 벤치라는, 코드 수정 능력을 평가하는 벤치마크"` (첫 등장 시 1회만 설명)
  - `try/catch` → `"트라이 캐치"`, `PR` → `"피알, 즉 코드 변경 요청"` (첫 등장 시)
  - `Ctrl+G` → `"컨트롤 지"`, `Alt+G` → `"알트 지"`
- 숫자 범위 `10~100` → `"열 배에서 백 배"` 또는 `"10에서 100"` (문맥에 맞게 읽기 쉽게).
- URL·해시·코드 조각 등 **소리로 의미 없는 것은 제거**한다.

### 4. 내용 충실성 & 깊이 (매우 중요)

기본 원칙: **"요약"이 아니라 "구어체 낭독용으로 다듬되 정보는 보존"** 이다. 사용자는 정보를 얻으려고 듣는다. 개요로 축약해 실제 알맹이를 날리면 안 된다.

- **원문에 없는 사실을 지어내지 않는다.** 설명을 덧붙이되, 새로운 주장/수치는 만들지 않는다.
- **글 성격에 따라 깊이를 다르게 한다:**
  - **정보 전달형**(기술 설명·튜토리얼·정리글·리스트형): 원문의 **모든 핵심 포인트/섹션을 빠짐없이** 담는다. 예를 들어 원문이 8개 항목·단계·레이어를 다루면 **8개를 모두** 풀어 읽는다. 구체적인 이름·수치·사례를 살린다. 한두 개만 설명하고 "이런 것들이 있다"로 뭉개지 말 것.
  - **뉴스·단신·감상·의견**: 요점 위주로 요약해도 된다.
  - 판단이 애매하면 **덜 요약하는 쪽**(정보 보존)을 택한다.
- 걷어내는 것은 **정보가 아니라 노이즈**다: 코드 조각, URL, 해시, 중복 표현, 소리로 의미 없는 것.
- 길이가 길어지는 건 괜찮다. **이해를 돕는 구조(예고·신호어·정리)는 유지**하되, 그 구조 때문에 알맹이를 빼지 않는다.

### 5. 출력 형식

- `script` 는 **순수 텍스트 한 덩어리** (마크다운 기호 `#`, `*`, `-` 금지 — TTS가 기호를 읽어버린다).
- 문장은 마침표로 끝맺어 TTS가 자연스럽게 끊어 읽게 한다.

## 예시 (일부)

원문 문단:
> 사람이 코드를 읽고 쓰지 않는 무인 소프트웨어 팩토리는 생성 속도를 높이지만, 장기 유지보수성을 판단할 인간까지 제거해 복잡한 프로덕션 코드베이스에서 작동하기 어려움

보정된 대본:
> 다음 글입니다. 이번 글은 사람 없이 코드를 만드는 이른바 '무인 소프트웨어 팩토리'가 왜 실패하는지에 대한 이야기입니다. 핵심부터 말씀드리면, 코드를 빨리 만들 수는 있어도 그 코드를 오래 관리하기는 어렵다는 것입니다. 먼저, 무인 소프트웨어 팩토리는 사람이 코드를 직접 읽거나 쓰지 않기 때문에 생성 속도는 분명히 빨라집니다. 그런데 문제는, 코드가 앞으로도 잘 유지될지 판단할 사람까지 없애버린다는 점입니다. 그래서 복잡한 실제 서비스 환경에서는 제대로 작동하기 어렵습니다.
